# 콘텐츠 규약

## 세 층과 공개 경계

`raw/`는 원자료, `wiki/`는 출처를 연결한 분석, `content/`는 홈페이지용 글이다. `AGENTS.md`가 각 층을 다루는 작업 규칙을 정의한다. LLM Wiki의 세 층인 원자료·wiki·schema에 홈페이지용 콘텐츠 층을 추가한 구성이다.

원자료 본문과 `raw/game-ai/`의 자료 모음은 `.gitignore` 대상이다. wiki, 공개 글의 초안, 출처 목록은 Git 관리 대상이다. 이 위치에는 비밀이나 비공개 개인정보를 기록하지 않는다. `.gitignore`는 이미 추적된 파일이나 기존 Git 이력을 제거하지 않는다.

홈페이지 빌드는 `content/manifest.json`의 목록에 등록된 문서만 페이지로 만든다. 문서가 없는 영역에는 빈 상태를 표시한다. 저장소 전체를 정적 파일 폴더로 복사하지 않는다. 공개 Git 저장소에서 보이는 파일은 사이트의 공개 목록과 별개다.

## 문서 메타데이터

`wiki/`의 지식 페이지와 `content/`의 글은 다음 frontmatter를 사용한다. README, index, log와 템플릿은 검사 예외다.

이 규약은 게시용 데이터 형식이다. 기술 공부·감상문의 본문 목차를 규정하지 않는다. 두 영역은 본문 템플릿 없이 실제로 읽은 원문의 구조와 성격에 맞춰 각각 작성한다.

```yaml
---
id: unique-kebab-case-id
title: 문서 제목
type: concept
status: reviewed
visibility: internal
created: 2026-11-18
updated: 2026-11-18
sources: ["src-llm-wiki"]
---
```

| 필드 | 규칙 |
| --- | --- |
| `id` | 저장소 안에서 고유한 소문자 kebab-case |
| `title` | 실제 내용을 설명하는 제목 |
| `type` | `source`, `concept`, `project`, `decision`, `profile`, `study`, `review` 중 내용에 맞는 값 |
| `status` | `draft`, `reviewed`, `archived` |
| `visibility` | wiki는 `internal`, content는 `public`. 의도한 독자이며 배포 상태가 아니다. |
| `created`, `updated` | 한국시간 기준 `YYYY-MM-DD`. 갱신일은 작성일보다 빠를 수 없다. |
| `sources` | `raw/manifest.json`의 출처 ID를 JSON 배열 형식으로 작성한다. 단순 파서와 YAML 양쪽에서 읽기 위한 제한이다. |
| `summary` | 선택 필드. 목록과 문서 머리에 표시할 짧은 요약 문자열 |
| `category` | 공개용 프로젝트·기술 공부·감상문에서 사용할 선택 필드. `content/categories.json`의 해당 분야에 등록한 ID 하나. 생략하면 미분류. 소개/CV에는 지정하지 않는다. |
| `references` | 공개 출처의 선택 필드. 한 줄 JSON 배열로 작성한다. 게시물별 `content/post-settings/<id>.json`이 있으면 해당 파일의 `references`가 기준이다. 내부 `sources`와 별개다. |

문서 ID와 출처 ID는 서로 다르다. 예를 들어 `source-llm-wiki` 페이지는 `src-llm-wiki` 원문을 근거로 삼는다. 확인이 끝나지 않은 필드는 본문에서 미확인으로 명시한다. 초안에 빈 출처 배열을 쓸 수 있지만 공개 목록에 넣을 수는 없다.

`reviewed`는 원문 대조와 문서 검토를 마쳤다는 뜻이다. 출처가 주장한 성능이나 효과를 독립적으로 재현했다는 뜻은 아니다. 확인한 범위를 본문에 적는다.

세부 카테고리는 문서 종류 아래의 탐색용 분류이며 본문 목차를 규정하지 않는다. `project`는 `projects`, `study`는 `tech`, `review`는 `hobby` 설정을 사용한다. 기본 홈페이지와 디자인 미리보기에서 같은 카테고리를 표시한다. 이름·순서·추가·글 지정 방법은 [카테고리 설정 안내](categories.md)를 따른다.

## 출처 목록

`raw/manifest.json`의 `version`은 `1`이다. 각 항목에는 다음 필드가 있다.

| 필드 | 의미 |
| --- | --- |
| `id`, `title` | 안정적인 출처 ID와 식별할 수 있는 제목 |
| `path`, `sha256` | 저장소 안의 원본 경로와 바이트 무결성 기준 |
| `acquired` | 이 저장소에 등록한 날짜 |
| `author`, `published`, `url` | 확인된 작성자·발행일·원문 URL. 모르면 `null` |
| `ingest_status` | `pending` 또는 `ingested` |
| `verification` | 제공 문서를 읽은 `provided-text`, 웹 원문을 보관하고 읽은 `web-text`, 아직 확인하지 않은 `unverified` |
| `wiki_page` | 수집 완료된 자료의 요약 경로. 대기 중에는 `null` |

새 검증 상태나 형식을 도입할 때는 규약과 검사기를 함께 수정한다. 상태 이름만으로 원문 내 주장의 정확성을 보증하지 않는다.

`web-text`는 저장한 원문과 요약을 대조했다는 뜻이다. 저자의 성능 수치를 재현하거나 본문에 연결된 모든 영상·이미지·코드를 확인했다는 뜻은 아니다. 확인한 범위를 출처 페이지와 공개 글에 적는다. 원문 보관 방식은 [웹 원문 수집](source-archiving.md)을 따른다.

## 공개 목록

`content/manifest.json`은 다음 형식이다. `path`는 저장소 루트 기준 Markdown 경로, `slug`는 사이트에서 사용할 경로다.

```json
{
  "version": 1,
  "pages": [
    { "path": "content/projects/example.md", "slug": "/projects/example", "featured": true }
  ]
}
```

등록된 글은 검토 완료 상태이며 출처가 있어야 한다. 본문에 미작성 표시나 내부 wiki·원자료로 향하는 링크를 남기지 않는다. 독자에게 보여 줄 근거는 공개 가능한 외부 링크나 향후 사이트 안의 공개 자료로 제공한다. 비공개 출처 ID와 검토 기록은 렌더러가 메타데이터로 처리하고 본문에 자동 출력하지 않는다.

| 글 종류 | 저장 위치 | 공개 경로 | 내용 |
| --- | --- | --- | --- |
| `project` | `content/projects/` | `/projects/<slug>` | 만든 결과물과 본인의 기여 |
| `study` | `content/study/` | `/study/<slug>` | 기술 개념, 질문과 실험 |
| `review` | `content/reviews/` | `/reviews/<slug>` | 취미의 작품·활동 감상 |
| `profile` | `content/profile.md` | `/about` | 소개와 연락처 |

빌드는 마지막 `/`를 붙인 주소로 통일한다. 종류·저장 위치·공개 경로가 맞지 않으면 검사와 빌드가 실패한다. 홈과 목록의 경로를 문서가 덮어쓸 수 없다. 소개 문서는 한 개만 등록한다.

`/projects/`, `/tech/`, `/hobby/`는 빌드가 만드는 분야 페이지다. 프로젝트·기술 공부·감상문을 각각 독립 목록으로 표시한다. 이 경로에 별도 Markdown을 등록하지 않는다. `/study/`와 `/reviews/` 및 기존 상세 글 경로도 유지한다.

홈의 자기소개는 공개 목록에 등록된 프로필의 `summary`를 사용한다. 요약이 없으면 소개 페이지로 안내하며 전체 CV를 메인에 펼치지 않는다. 미등록 초안은 읽어 표시하지 않는다. 소개 페이지에는 공개 프로필 본문을, 프로필이 없으면 빈 CV 양식을 표시한다. 홈의 프로젝트·기술·취미 미리보기는 클릭과 키보드로 전환하며 각각의 독립 페이지에도 연결한다.

`featured`는 프로젝트에만 사용할 수 있는 호환 메타데이터다. 현재 화면에는 별도의 대표 프로젝트 영역이 없다. 프로젝트·기술 공부·감상문은 각각 `created` 내림차순으로 정렬하고 홈에 영역별 최신 글을 최대 5개 표시한다. 카테고리의 글 수는 최신 5개가 아니라 전체 공개 글을 기준으로 센다.

감상문도 출처 연결을 유지하되 사용자의 원본 감상 메모를 작성 근거로 삼을 수 있다. `reviewed`는 제공한 감상과 글을 대조하고 공개 범위를 검토했다는 뜻이다. 개인적 느낌에 객관적 증명을 요구하지 않는다. 작품의 사실 정보는 확인된 범위로 작성한다.

## 링크와 수식

저장소 문서 연결은 상대 경로 Markdown 링크를 사용한다. 공개 글에서는 공개 목록에 등록된 문서의 상대 Markdown 링크 또는 사이트 경로를 사용할 수 있다. 빌드는 상대 문서 링크를 실제 사이트 주소로 바꾸며 미등록 문서·존재하지 않는 경로로 향하면 실패한다. Obsidian 전용 wikilink에 의존하지 않는다. wiki는 index에 등록하고 관련 페이지끼리 의미 있는 링크를 연결한다. 외부 링크는 실제 읽은 원문을 표시하되 아직 방문하지 않은 링크를 검증 완료로 기록하지 않는다.

이 저장소의 wiki는 Obsidian에서도 읽을 수 있는 Markdown이다. Obsidian용 문서의 수식은 `$$` 구분자를 사용한다.

## 현재 웹 렌더러의 범위

웹 출력은 제목·문단·단순 목록·인용·코드·강조·일반 링크·단순 표를 지원한다. 본문의 첫 `# 제목`은 frontmatter의 `title`과 같아야 하며, 상세 화면에서 제목을 중복 출력하지 않는다.

HTML은 실행하지 않고 문자로 표시한다. 중첩 목록과 여러 줄 목록 항목은 현재 지원하지 않으며 빌드 오류로 알린다. 참조형 링크와 수식은 별도 해석 없이 문자로 남는다. Obsidian의 수식 작성 규칙과 웹에서 수식을 조판하는 기능은 별개다.

기본 홈페이지와 DevBlog 미리보기는 별도 한 줄의 Markdown 이미지와 `:::video`·`:::youtube` 블록을 지원한다. 첨부는 해당 게시물의 `content/media/<id>/`에 보관하고, 화면 표시와 공개용 출처는 `content/post-settings/<id>.json`에서 관리한다. 기본 빌드는 공개 글에서 참조한 첨부만 `dist/media/`에 복사한다. 전용 테스트 예제와 그 첨부는 별도 미리보기 빌드에만 포함한다. 임의 HTML이나 원자료 폴더를 공개하는 기능은 아니다.

공개용 출처 영역은 자료가 있을 때만 본문 하단에 표시한다. 제목·URL과 필요한 작성자·발행일·참고 범위를 적으며 본문 목차나 필수 소제목을 강제하지 않는다. 미등록 초안의 본문을 읽어 화면에 추가하지 않는다. [글·문구·미디어 편집 안내](media-authoring.md)에 작성 문법과 로컬 편집기 사용법을 정리했다.

기존 기술 글 21편의 출처 28개는 기본 홈페이지와 미리보기의 하단 영역에 표시한다. `referenceBlocks`에 대조해 둔 말미 문구만 화면에서 제외하며 원본 Markdown과 본문 중 근거 링크는 보존한다. 변경된 말미 문구는 일치 검사에서 오류로 알려 재대조한다. 기본 빌드 적용은 로컬 정적 결과 생성이며 원격 배포를 뜻하지 않는다.
